# sensors-ui — клієнтський застосунок (Next.js)

Інтерфейс моніторингу давачів температури та диму. Сторінки з графіками беруть
дані із серверного застосунку `sensors-api`, який зберігає їх у базі даних
PostgreSQL. З лаб. №6 сторінки також показують сповіщення про критичні
показання, які сервер надсилає через Server-Sent Events.

## Запуск у Docker

З папки на рівень вище (там лежить `docker-compose.yml`):

```
docker compose up --build
```

Сайт: http://localhost:3001. Адреса сервера (`http://localhost:3000`)
вшивається в код під час збирання образу — вона задана в `docker-compose.yml`.

## Запуск локально без Docker

```
copy .env.example .env
npm install
npm run dev
```

Відкрийте http://localhost:3001. Порт 3001 обрано, щоб не конфліктувати із
сервером NestJS на 3000.

Адреса сервера задається у файлі `.env`:

```
NEXT_PUBLIC_API_URL=http://localhost:3000
```

Для сервера на Render підставте `https://<назва>.onrender.com`. Після зміни
`.env` перезапустіть `npm run dev`.

## Розгортання на Vercel

Імпортуйте репозиторій, Framework Preset — Next.js. У **Environment Variables**
додайте `NEXT_PUBLIC_API_URL` з адресою сервера на Render. Файл `.env` у
репозиторій не потрапляє (він у `.gitignore`), тому без цієї змінної сайт не
знатиме адреси сервера. Після зміни змінної потрібен Redeploy.

## Сторінки

| Адреса | Файл | Що там |
|---|---|---|
| `/` | `app/page.tsx` | опис і адреса сервера, з яким працює клієнт |
| `/dashboard-temp` | `app/dashboard-temp/page.tsx` | графік температури з `GET /temperature-sensors`; сповіщення з `/temperature-sensors/alerts` |
| `/dashboard-smoke` | `app/dashboard-smoke/page.tsx` | графік диму з `GET /smoke-sensors`, поріг і тривога із сервера; сповіщення з `/smoke-sensors/alerts` |
| `/login` | `app/login/page.tsx` | форма входу, поля й кнопка заблоковані |

## Структура

```
app/                    сторінки (App Router: папка = адреса)
components/
  Navbar.tsx            навігація
  SensorChart.tsx       графік recharts, спільний для обох давачів
  StatCard.tsx          картка з одним показником
  DataState.tsx         повідомлення замість графіка: завантаження / помилка / порожньо
  AlertList.tsx         лаб. №6: стан SSE-з'єднання і червоні блоки сповіщень
lib/
  api.ts                адреса сервера з NEXT_PUBLIC_API_URL і типи записів та сповіщень
  useSensorData.ts      хук: GET кожні 5 с і POST нового показання
  useAlerts.ts          лаб. №6: хук, що відкриває EventSource і тримає останні 5 сповіщень
  chart.ts              розрахунок поділок осі Y
Dockerfile              як зібрати образ застосунку
.dockerignore           що не потрапляє в образ
.env                    адреса сервера для локального запуску (не потрапляє в Git)
.env.example            зразок .env (потрапляє в Git)
```

## Як сторінка отримує дані

1. `useSensorData("/smoke-sensors", 5000)` робить `fetch(API_URL + path)` одразу
   після відкриття сторінки і далі кожні 5 секунд.
2. Сервер читає з бази 50 останніх записів і повертає їх від старих до нових;
   сторінка бере останні 20 і перетворює кожен на точку графіка: `time` — з
   `timestamp`, `value` — з `value`.
3. Для диму поля `alarm` і `threshold` приходять із сервера готовими — клієнт
   тривогу не рахує, а лише показує.
4. Кнопка «Додати показання» надсилає POST на той самий маршрут і перечитує записи.

## Як сторінка отримує сповіщення (лаб. №6)

1. `useAlerts("/temperature-sensors/alerts")` створює `new EventSource(API_URL + path)`.
   Браузер надсилає один GET-запит, і сервер лишає з'єднання відкритим.
2. Коли сервер зберігає критичне показання, він дописує в це з'єднання подію.
   У браузері спрацьовує `onmessage`, сповіщення стає першим у списку;
   лишаються останні 5.
3. Якщо з'єднання обірвалося (сервер перезапустили, зник інтернет), браузер
   сам підключається знову. Стан видно в рядку над сповіщеннями.
4. Сповіщення живуть лише в пам'яті сторінки: після F5 список порожній.
   Сервер надсилає подію тим, хто підключений у цю мить, і не зберігає її.
5. Кнопки «Імітувати мороз» та «Імітувати задимлення» надсилають звичайний
   POST із критичним значенням. Сповіщення при цьому приходить не у відповідь
   на POST, а окремо — через SSE.
